Prompt final à utiliser pour terminer le frontend MVP
Rôle
Tu es un lead frontend engineer, architecte React et product designer senior. Finalise le frontend web du module Hôpital de la plateforme Isoko Hub en t’appuyant sur l’implémentation existante et sur les spécifications fonctionnelles fournies.

Ne recrée pas les fonctionnalités déjà présentes. Inspecte et réutilise les composants, modèles frontend, routes et dashboards existants. Complète uniquement ce qui manque, harmonise l’expérience et rends les parcours réellement navigables.

Le MVP doit rester volontairement limité. Ne développe pas maintenant :

le spécialiste distant ou médecin partenaire de la diaspora ;
le coordinateur de télémédecine ;
l’agent du service clientèle / support.
Ne crée pas leurs dashboards, menus, permissions, routes ou workflows. Garde uniquement une architecture extensible pour pouvoir les ajouter dans une phase ultérieure.

Stack obligatoire
React avec TypeScript ;
Tailwind CSS ;
React Router ;
architecture par fonctionnalités ;
composants réutilisables ;
données et appels API compatibles avec le backend Django existant ;
ne pas remplacer Django par un autre backend ;
ne pas créer de nouvelle base de données ;
ne pas modifier les modèles backend sauf si une incompatibilité évidente est signalée séparément ;
ne pas exposer de secrets ;
utiliser des mocks uniquement lorsque l’API n’existe pas encore, avec une couche de service facilement remplaçable.
Périmètre
Construire et finaliser les espaces web professionnels de l’hôpital :

administrateur d’hôpital ;
médecin local ;
infirmier/infirmière ;
laborantin ;
caissier/agent de facturation ;
agent d’accueil/admissions ;
éventuellement responsable de laboratoire, responsable financier et directeur médical.
Les trois rôles suivants sont reportés après le MVP et ne doivent pas apparaître dans la navigation actuelle :

spécialiste distant / médecin partenaire diaspora ;
coordinateur de télémédecine ;
agent du service clientèle / support.
La partie publique existante et l’application patient/mobile ne doivent pas être supprimées. Elles doivent continuer à fonctionner, mais le travail principal concerne les espaces professionnels inclus dans le MVP.

Règle principale de sécurité UX
Mettre en place un contrôle d’accès par rôle côté frontend avec un RoleGuard ou PermissionGuard. Le frontend doit masquer ou désactiver les fonctions non autorisées, mais ne jamais prétendre remplacer les contrôles de sécurité du backend.

Les données médicales doivent être affichées selon le principe du moindre privilège :

le caissier voit les données nécessaires à la facturation, pas les notes cliniques ;
l’agent d’accueil voit les données administratives nécessaires, pas le dossier médical complet ;
le médecin et l’infirmier accèdent uniquement aux patients concernés par leur prise en charge.

Critères d’acceptation
Le travail est terminé si :

Les dashboards existants sont conservés et visuellement harmonisés.
Le profil de chaque rôle possède un parcours cohérent.
L’administrateur peut gérer les établissements, services, médecins, horaires, utilisateurs et statistiques.
L’agent d’accueil peut gérer une arrivée, une file d’attente et un rendez-vous.
Le médecin peut consulter un patient autorisé et rédiger une note de consultation.
L’infirmier peut saisir les constantes et suivre les soins.
Le laborantin peut suivre une analyse et saisir un résultat.
La validation d’un résultat est séparée de sa simple saisie lorsque les permissions l’exigent.
Le caissier peut gérer une facture, un paiement et un reçu sans voir inutilement le dossier clinique.
Les trois fonctionnalités suspendues ne figurent pas dans la navigation du MVP.
Les permissions modifient effectivement les actions visibles.
Les états de chargement, erreur, vide et succès sont traités.
Les informations médicales et financières sont visuellement séparées.
L’application reste utilisable sur desktop et tablette.
Les routes sont navigables sans écran fictif ou lien cassé.
Aucun backend ou secret n’est ajouté dans le frontend.
Le code existant est réutilisé au lieu d’être dupliqué.
Les fonctionnalités reportées sont signalées proprement dans le code et dans le README.
